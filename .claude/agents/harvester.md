## L4 / L3 calculus + pseudo-language conventions (governed by the semantic surface)

For operators harvested at **L4 or L3**, the canonical reference is the **active-management SEMANTIC SURFACE** `book/src/semantics/index.md` (the surface got its own home at cycle-116, relocated from the former `book/src/design/l4_calculus.md`; promoted out of "strawman" status 2026-06-06; user directive 2026-05-27, mid-cycle-006; CLAUDE.md §Methodology-invariant "SEMANTIC CONSOLIDATION"; memory `project_semantic_consolidation_surface`). Cite and continue it; do not displace it. Signatures, body shapes, and reduction rules in your L4/L3 operator entry must use the surface's notation.

- **USE + LINK, don't RE-STATE the general semantic rule (user directive 2026-06-06).** A semantic rule/def/abstraction about the language (the named-shape-groups binding/use syntax + anti-pattern, the closure-returning-signature convention, the notation invariant, a monad/ownership/reduction convention) lives ONCE, on the semantic surface. Your operator entry carries its **OWN** concrete shape/semantic fact (e.g. "`dot` is whole-tensor-reduce: `Tensor[(S: ...)] → Tensor[(S: ...)] → Scalar`") + a **pointer to the governing §** (e.g. "see `book/src/semantics/index.md` §1.2.1") — it does NOT transcribe the general binding/use teaching or the `Tensor[N]`-anti-pattern explanation. Restating a general rule at the operator scope is the semantic analog of a degenerate identity-lowering smell; if you find yourself writing the general teaching, link instead. (The named-shape-groups + closure-signature bullets below are the producer-side reminders of the rule's *application*; the rule's *definition* lives on the surface.)

- **Closure-returning / high-order signatures — group the closure, use the operator-VALUE spelling, do NOT write the opaque type-application form** (user directive 2026-06-07; authoritative def `book/src/semantics/index.md` §1.3.1; memory `project_closure_returning_signature_convention`). The L4 calculus is **high-order** — a signature's codomain may itself be a function. When you write a high-order signature (an operator constructor, a curried/partial-application factory, anything whose *intended use is to yield a closure applied later*): (i) for a **bare returned function**, group the closure sub-signature in parens — `example :: foo -> (bar -> baz)` (the parens are a reader-intent marker: "the codomain is a closure you hold and apply, not the last operand"); (ii) for a returned **operator instance** carrying closed-over `!`-params (FE space / basis / geometry tables / factorizations), use the operator-VALUE spelling `Op[τ_in → τ_out]` (or the square-operator `LinOp[(N: ...), $N]` / two-group `LinOp[(R: ...), (D: ...)]` of §1.2.2) — the bracket already carries the in/out arrow, so it is ALREADY COMPLIANT and wants **no** outer parens (an operator **constructor** `mk :: A -> Op[X → Y]` or **transformer** `t :: Op[X → Y] -> Op[X' → Y']` stands as-is). **Do NOT write the opaque type-application form** `LinearOperator[N,N]` / `LinearOperator (Tensor[…])` — applying a bare type name to dim/arg slots hides the higher-order intent and is the **non-compliant smell**; the fix is to **re-spell** in the bracketed operator-value form, NOT to wrap the opaque form in parens. Cite + link §1.3.1; do not restate the convention.

- **Signatures**: Haskell `::` arrow form — `f :: A -> B -> C`.
- **Records**: TypeScript brace form — `{ field: type }`.
- **Body shapes**: Haskell-style do-notation (`do { let x = e; modify f; pure r }`) and lambda (`\s -> ...`).
