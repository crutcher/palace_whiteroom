## Why P0-first, and what "P0" mechanically IS this cycle

The single most important on-disk finding driving this plan: **the artifact has no uniform machine-readable dependency representation today.** Dependency information lives in THREE incompatible places:
1. `depends_on:` frontmatter — present in only **10 of 357** `book/src/*.md` files (pasted evidence below);
2. prose `## Dependencies` sections + the `L_n/index.md` dep-map tables (the bulk; free text, not parseable);
3. feature `composes:` / `l0_ground_truth:` frontmatter (the 15 feature columns).

And **253 of 357 files carry NO maturity frontmatter at all** (`firmness:`/`status:`/`kind:`) — they are index pages, lowering themes, L2/L3/L0 entries, and concept pages whose status (where they have one) lives only in prose.

Consequence for P0: a linter cannot be run artifact-wide until a uniform scheme is *defined and populated*. So P0 this cycle is precisely two coupled deliverables:
- **(A) the canonical scheme** — a normative authoring convention: a per-chapter machine-readable frontmatter block carrying (i) the node's `rank` token (mapping the existing `firmness:`/`status:` vocabulary onto the ladder `roadmap_goal=0 < stub=1 < rough-in=2 < firm=3`, with `partly-constructive`/`rough-in (test-coverage-bounded)` ≈ 2.5 sub-rank and `obstruction` as a separate rankable kind), (ii) typed edges (`depends-on` blocking / `reference` free; an edge to a feature root is `reference`; optional ignored `kind:`), (iii) the feature-root marker (`seed` as a parallel root-set axis, NOT a ladder rung). The scheme MUST also specify the migration mapping from the three existing representations so P1 is mechanical.
- **(B) the two linters** — `tools/` Python tools (the `citecheck` layout is the model: `<tool>.py` + `README.md` + `requirements.txt`) that parse the scheme: a **rank linter** (`rank(u) ≤ min over depends-on deps`; emits violations + the promotion frontier) and a **reachability GC** (mark from feature-root nodes over `depends-on` edges; unmarked = garbage; emits detritus + per-file inbound-reference report). Validated against a **seed fixture** (a small hand-typed graph) + a dry run over the existing `depends_on:`-frontmatter subset, so they are demonstrably correct BEFORE P1 populates the artifact. The linters emit "untyped/missing-frontmatter" diagnostics (most of the tree, pre-P1) as warnings, not hard failures, so they are runnable incrementally during the P1 rollout.

This is the `METHODOLOGY-GRADED-STACK.md` §3 (shared substrate / minimal binary) + §4 (two linters) + §5 (adoption: audit-first) reading: keep the scheme minimal so the unavoidable P1 typing pass is cheap; the linters exist first so the typing pass IS the audit.
